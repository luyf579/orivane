# Orivane v0.1.1

This patch fixes CLI trace compatibility with byte-valued OpenTelemetry attributes.

## Trace compatibility fix

OpenTelemetry 1.45 retains byte-valued span attributes. The v0.1.0 CLI passed
allowlisted values directly to JSON formatting, so a bytes value could raise
TypeError and make an otherwise successful `orivane trace` invocation exit with 1.
The patch normalizes those values at the private trace-formatting boundary.
Application failure exit codes and error categories remain unchanged.

The normalization contract is:

- Preserve strings, booleans, integers, floats and None.
- Decode valid UTF-8 bytes into strings.
- Recursively normalize lists and tuples into JSON arrays.
- Replace invalid UTF-8 bytes with the fixed structural marker `<bytes>`.
- Replace unsupported values with the fixed structural marker `<unsupported>`.

No byte repr, hex, base64 or raw value fallback is printed. The existing attribute
allowlist is unchanged. Prompts, inputs, outputs, tool arguments/results, session
payloads, raw exception messages, native events and status descriptions are not
added to structural trace output. Applications must continue to use nonsensitive
values for allowlisted structural attributes. Requested application output remains
separate from the structural trace section.

## Compatibility and scope

Core, backend and Commerce runtime code and public APIs are unchanged. CLI keeps
its existing init, validate, run and trace commands; the normalization helper is
private. All four package versions and the virtual workspace are synchronized at
0.1.1. Backend requires Core 0.1.1; CLI requires Core and backend 0.1.1. Commerce
continues to depend only on Pydantic.

PydanticAI and pydantic-graph remain pinned to **2.48.0**. Core continues to declare
`opentelemetry-api>=1.44,<2`; CLI continues to declare
`opentelemetry-sdk>=1.44,<2`. External development-lock dependencies are unchanged.
Release workflow semantics are unchanged; artifact paths were synchronized
to the 0.1.1 distribution filenames.
